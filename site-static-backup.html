Topics

From “send” to “response” slides 1-3

The session opens the black box between “send” and “response”: what Day 1’s words actually measure, which stage of a request each belongs to, and why it matters once real users arrive — because in production you own speed, cost, capacity and reliability, and each idea maps to a decision you will be asked to make.

Example · slide 3“Calling a model is the easy part. In production you own what happens around it: speed, cost, capacity and reliability.”

Vocabulary, deepened slides 4-5

A Day 1 refresher (latency is how fast one request starts; throughput is how many we serve at once) plus the four new ideas that decide real-world speed: batching, concurrency, queueing and cold starts.

Example · slide 5“batching (process requests together), concurrency (many in flight at once), queueing (waiting for a free slot) and cold starts (the delay before a sleeping model can answer).”

The six-stage inference pipeline slides 6-10

Every request passes the same stages: it arrives as token IDs, may wait in a queue, has its prompt read in one pass (prefill), emits the first token, then generates tokens one at a time (decode). Queue waiting is part of TTFT and under heavy load often dominates it; a longer prompt means a higher TTFT; the gap between two consecutive tokens is TPOT, and it sets how fast text streams.

Example · slide 8“If every slot is busy, it waits in a queue. That waiting time is part of TTFT, and under heavy load it often dominates it.”

KV cache and the latency formulas slides 11-14

Attention needs the keys (K) and values (V) of every earlier token; the KV cache computes each token’s K and V once, stores and reuses them — but it bills memory for every token, in every layer, for every request in the batch (about 0.8 MB per token for a 13B model), competing with the weights and setting how many requests fit at once. Slide 14 ties it together: TTFT = queueing + prefill, TPOT = decode time per token, total latency roughly TTFT + (output tokens - 1) x TPOT.

Example · slide 14“TTFT = queueing + prefill. TPOT = decode time per token. Total latency is everything combined, roughly TTFT + (output tokens - 1) x TPOT.”

Batching strategies and scheduling slides 13, 15-16

To keep an expensive GPU busy, providers batch many requests together: throughput rises, but your own request may have to wait for the batch. Static batching waits for the slowest request, so finished slots sit idle; continuous (iteration-level) batching refills a freed slot at the very next step, so the GPU stays full and newcomers wait less. Each step the scheduler decides who joins the batch — long prompts get sliced so they cannot stall everyone’s decoding, and when KV memory runs out requests are paused or turned away; these choices shape your p99.

Example · slide 15“Static batching waits for the slowest request before starting anything new, so finished slots sit idle. Continuous (iteration-level) batching refills a freed slot at the very next step.”

Cost-latency trade-offs and routing slides 17-19

Bigger is not always better: larger models are usually stronger but slower and pricier per token, while smaller models are cheaper and snappier but weaker on complex tasks — latency, cost and quality move together. Picking a model is a trade-off, not a ranking, and instead of one model for everything a router can pick the model per request: easy ones to a small, fast model, hard ones to a large, careful one.

Example · slide 18“Ask: how long can this task wait, and how wrong can it afford to be? There is no universal answer.”

Monitoring and symptom triage slides 20, 25

Average latency hides most of these problems, so teams watch a small dashboard: percentiles for TTFT and TPOT, token counts, queue and cache health, and output quality. In production nobody tells you “the KV cache is full” — you get symptoms, and knowing the concepts turns a vague complaint into a short list of suspects, each living in one stage of the pipeline.

Example · slide 20“Average latency hides most of these problems. Teams watch a small dashboard: percentiles for TTFT and TPOT, token counts, queue and cache health, and output quality.”

Failures at scale: four cases slides 21-24

Four documented failures: in GPT-2/3’s tokenizer, usernames from Reddit’s r/counting forum such as ‘SolidGoldMagikarp’ became single tokens yet barely appeared in the training data, so the models denied, hallucinated or produced gibberish about them (slide 21); GPT-4o launched in May 2024 with a new 200k-token tokenizer whose longest Chinese tokens were spam, gambling and adult-site phrases, learned from a corpus polluted by hijacked web pages (slide 22); Anthropic’s routing bug, which sent short-context requests to servers set up for the 1M-token context window — at the worst hour 16% of Sonnet 4 requests were affected, and sticky routing kept some users on the wrong servers (slide 23); and 60-80% of KV-cache memory wasted by 2023 serving systems on fragmentation and over-reservation, which PagedAttention cut below 4% and turned into a 2-4x throughput gain (slide 24). Slide 28’s caveat travels with all of them: the figures are as reported by their authors and are not independently verified.

Example · slide 24“Berkeley’s vLLM team found that 2023 serving systems wasted 60-80% of KV-cache memory on fragmentation and over-reservation, which capped batch sizes. Paging the cache (PagedAttention) cut waste below 4% and raised throughput 2-4x.”

Exam takeaways

  1. The latency formulas: TTFT = queueing + prefill; TPOT = decode time per token; total latency is roughly TTFT + (output tokens - 1) x TPOT. slide 14
  2. What the KV cache costs: about 0.8 MB per token for a 13B model — K and V for every token, in every layer, for every request in the batch — competing with the weights for GPU memory and setting how many requests fit at once. slide 12
  3. Model choice is a trade-off, not a ranking: ask how long the task can wait and how wrong it can afford to be — latency, cost and quality move together. slides 17-18

Glossary

Tokenizer slide 7
Cuts text into tokens; from stage 1 on, everything the model sees is a sequence of token IDs.
Prefill slide 9
The model reads the entire prompt in one pass, builds its internal state, then emits the first token; a longer prompt means a higher TTFT.
Decode slide 10
Each new token depends on the tokens before it, so the model produces them one at a time.

Measured as queueing + prefill; the queueing share often dominates under heavy load.
TPOT slides 10, 14

Each token’s keys and values are computed once, stored and reused instead of recomputed at every step.

Continuous (iteration-level) batching slide 15
Refills a freed slot at the very next step, keeping the GPU full.
Scheduler slide 16
